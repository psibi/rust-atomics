* Chapter 2: Atomics

In computer science, the word *Atomics* is used to describe an
operation that is indivisible: it is either fully completed, or it
didn’t happen yet.

Atomic operations are the main building block for anything involving
multiple threads. All the other concurrency primitives, such as
mutexes and condition variables, are implemented using atomic
operations.

In Rust, atomic operations are available as methods on the standard
atomic types that live in std::sync::atomic. They all have names
starting with Atomic, such as AtomicI32 or AtomicUsize.

Provides method for storing and loading:
- methods for atomic ~fetch-and-modify~ operations
- advanced ~compare-and-exchange~ methods.

* Memory Ordering

- Every atomic operation takes an argument of type
  *std::sync::atomic::Ordering*, which determines what guarantees we
  get about the relative ordering of operations.
- The simplest variant with the fewest guarantees is
  *Relaxed*. Relaxed still guarantees consistency on a single atomic
  variable, but does not promise anything about the relative order of
  operations between different variables.
- What this means is that two threads might see operations on
  different variables happen in a different order. For example, if one
  thread writes to one variable first and then to a second variable
  very quickly afterwards, another thread might see that happen in the
  opposite order.
- This chapter looks at examples where *Relaxed* ordering is not a
  problem.

* Atomic Load and Store Operations

#+begin_example rust
impl AtomicI32 {
    pub fn load(&self, ordering: Ordering) -> i32;
    pub fn store(&self, value: i32, ordering: Ordering);
}
#+end_example

Both the load and store are done atomically. (Duh!)

** Example: Stop flag

Use case: Informing other threads to stop running.

#+begin_src rust :crates '((rand . 0.8.5)) :results value verbatim :exports both
  use std::sync::atomic::AtomicBool;
  use std::sync::atomic::Ordering::Relaxed;

  fn some_work() {
      println!("child thread: hello world");
      std::thread::sleep(std::time::Duration::from_secs(2));
  }

  fn main() {
      static STOP: AtomicBool = AtomicBool::new(false);

      // Spawn a thread to do the work.
      let background_thread = std::thread::spawn(|| {
	  while !STOP.load(Relaxed) {
	      some_work();
	  }
      });

      // Use the main thread to perform some work
      loop {
	  println!("main thread: bye");
	  std::thread::sleep(std::time::Duration::from_secs(2));
	  let random: u8 = rand::random();
	  if random > 100 {
	      break;
	  }
      }

      // Inform the background thread it needs to stop.
      STOP.store(true, Relaxed);

      // Wait until the background thread finishes.
      background_thread.join().unwrap();
  }
#+end_src

#+RESULTS:
: main thread: bye
: child thread: hello world
: child thread: hello world

Cons: If the function `some_work()` gets stuck for a long time, that
can result in unacceptable delay beetween the time when it is stopped
and the program actually quitting.

Observation:
- It works because the flag is regularly checked by the background
  thread.

** Example: Progress reporting

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicUsize;
  use std::sync::atomic::Ordering::Relaxed;

  fn process_item(i: usize) {
      println!("Work done: {i}");
      std::thread::sleep(std::time::Duration::from_millis(500));
  }

  fn main() {
      let now = std::time::Instant::now();
      let num_done = AtomicUsize::new(0);

      std::thread::scope(|s| {
	  // A background thread to process all 5 items.
	  s.spawn(|| {
	      for i in 0..5 {
		  process_item(i); // Assuming this takes some time.
		  num_done.store(i + 1, Relaxed);
	      }
	  });

	  // The main thread shows status updates, every second.
	  loop {
	      let n = num_done.load(Relaxed);
	      if n == 5 {
		  break;
	      }
	      println!("Working.. {n}/5 done");
	      std::thread::sleep(std::time::Duration::from_secs(1));
	  }
      });

      println!("Done in {} ms!", now.elapsed().as_millis());
  }
#+end_src

#+RESULTS:
: Working.. 0/5 done
: Work done: 0
: Work done: 1
: Working.. 1/5 done
: Work done: 2
: Work done: 3
: Working.. 3/5 done
: Work done: 4
: Done in 3000 ms!

Cons: Once the last item is processed, it *might*, it might take one
while second for the main thread to know introducing an unnecessary
delay at the end.

Observation:
- In the function process_item, we have observable side effects
  (println), so the statements inside the background thread won't
  reorder.

** Synchronization

We can improve the above delay, using thread parking:

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicUsize;
  use std::sync::atomic::Ordering::Relaxed;

  fn process_item(i: usize) {
      println!("Work done: {i}");
      std::thread::sleep(std::time::Duration::from_millis(500));
  }

  fn main() {
      let now = std::time::Instant::now();
      let num_done = AtomicUsize::new(0);

      let main_thread = std::thread::current();

      std::thread::scope(|s| {
	  // A background thread to process all 5 items.
	  s.spawn(|| {
	      for i in 0..5 {
		  process_item(i); // Assuming this takes some time.
		  num_done.store(i + 1, Relaxed);
		  main_thread.unpark();
	      }
	  });

	  // The main thread shows status updates, every second.
	  loop {
	      let n = num_done.load(Relaxed);
	      if n == 5 {
		  break;
	      }
	      std::thread::park_timeout(std::time::Duration::from_secs(1));
	  }
      });

      println!("Done in {}ms!", now.elapsed().as_millis());
  }
#+end_src

#+RESULTS:
: Work done: 0
: Work done: 1
: Work done: 2
: Work done: 3
: Work done: 4
: Done in 2500ms!

You can see that that this program finishes faster!

** Example: Lazy Initialization

Use case: Calculate a result the first time it's required, and then
remember the result.

The program assumes that the value cannot be ever zero for simplicity:

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicU64;
  use std::sync::atomic::Ordering::Relaxed;

  fn calculate_x() -> u64 {
      println!("Computing x...");
      2
  }

  fn get_x() -> u64 {
      static X: AtomicU64 = AtomicU64::new(0);
      let mut x = X.load(Relaxed);
      if x == 0 {
	  x = calculate_x();
	  X.store(x, Relaxed);
      }
      x
  }

  fn main() {
      let x = get_x();
      let y = get_x();
      println!("{x},{y}");
  }
#+end_src

#+RESULTS:
: Computing x...
: 2,2

You can see that `Computing` got printed only once. *static* makes it
to available for all threads.

Cons: If a second thread calls ~get_x~ while the first one is still
calculating ~x~, the second thread will also start calcuating the
value. This might not be a good strategy for some use cases.

Rust standard library provides a better version through
*std::sync::Once* and *std::sync::OnceLock*.

Comment regarding memory ordering:
- Because of write-write coherence, operations on a single atomic
  object are always ordered ([[https://stackoverflow.com/a/78906962/1651941][Reference]]). So no re-ordering can take
  place here.

* Fetch and Modify Operations

- These operation load and modify the value as a single atomic
  operation.

Example function signature for AtomicI32:

#+begin_example rust
impl AtomicI32 {
    pub fn fetch_add(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_sub(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_or(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_and(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_nand(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_xor(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_max(&self, v: i32, ordering: Ordering) -> i32;
    pub fn fetch_min(&self, v: i32, ordering: Ordering) -> i32;
    pub fn swap(&self, v: i32, ordering: Ordering) -> i32; // "fetch_store"
}
#+end_example

- fetch_add increments and returns the original value (the value
  before incrementing)
- An important thing to keep in mind is that fetch_add and fetch_sub
  implement wrapping behavior for overflows.  This is different than
  the behavior of the plus and minus operators on regular integers,
  which will panic in debug mode on overflow.

** Example: Progress Reporting with Multiple threads

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicUsize;
  use std::sync::atomic::Ordering::Relaxed;
  use std::thread;
  use std::time::Duration;

  fn process_item(item: usize) {
      let _foo = item + 5;
      ()
  }

  fn main() {
      let num_done = &AtomicUsize::new(0);

      thread::scope(|s| {
	  // Four background threads to process all 100 items, 25 each.
	  for t in 0..4 {
	      s.spawn(move || {
		  for i in 0..25 {
		      process_item(t * 25 + i); // Assuming this takes some time.
		      num_done.fetch_add(1, Relaxed);
		  }
	      });
	  }

	  // The main thread shows status updates, every second.
	  loop {
	      let n = num_done.load(Relaxed);
	      if n == 100 {
		  break;
	      }
	      println!("Working.. {n}/100 done");
	      thread::sleep(Duration::from_secs(1));
	  }
      });

      println!("Done!");
  }
#+end_src

#+RESULTS:
: Working.. 0/100 done
: Done!

Observation:
- Theoretically there can be reordering between process_item function
  and atomic operation on num_done because there is no observable side
  effect on the process_item function.
- There are four threads and we don’t know in which order the threads
  will increment num_done, but as the addition is atomic, we don’t
  have to worry about anything and can be sure it will be exactly 100
  when all threads are done.

** Example: Statistics

Usecase: In the previous program, I want two statistics information:
- Average processing time
- Peak processing time

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::Ordering::Relaxed;
  use std::sync::atomic::{AtomicU64, AtomicUsize};
  use std::thread;
  use std::time::Duration;

  fn process_item(item: usize) {
      let _foo = item + 5;
      std::thread::sleep(Duration::from_millis(5));
      ()
  }

  fn main() {
      let num_done = &AtomicUsize::new(0);
      let total_time = &AtomicU64::new(0);
      let max_time = &AtomicU64::new(0);

      thread::scope(|s| {
	  // Four background threads to process all 100 items, 25 each.
	  for t in 0..4 {
	      s.spawn(move || {
		  for i in 0..25 {
		      let start = std::time::Instant::now();
		      process_item(t * 25 + i); // Assuming this takes some time.
		      let time_taken = start.elapsed().as_micros() as u64;
		      num_done.fetch_add(1, Relaxed);
		      total_time.fetch_add(time_taken, Relaxed);
		      max_time.fetch_max(time_taken, Relaxed);
		  }
	      });
	  }

	  // The main thread shows status updates, every second.
	  loop {
	      let total_time = Duration::from_micros(total_time.load(Relaxed));
	      let max_time = Duration::from_micros(max_time.load(Relaxed));
	      let n = num_done.load(Relaxed);
	      if n == 100 {
		  break;
	      }
	      if n == 0 {
		  println!("working.. Nothing done yet");
		  thread::sleep(Duration::from_millis(100));
	      } else {
		  println!(
		      "Working.. {n}/100 done, {:?} average, {:?} peak",
		      total_time / n as u32,
		      max_time
		  );
		  thread::sleep(Duration::from_millis(50));
	      }
	  }
      });
      println!("Done!");
  }
#+end_src

#+RESULTS:
: working.. Nothing done yet
: Working.. 76/100 done, 5.112697ms average, 5.418ms peak
: Done!

Observations:
- Possible for main thread to load the values after background thread
  has incremented ~num_done~, but before it has updated ~total_time~
  resulting in an underestimate of the average.
- Since Relaxed ordering gives no guarantees about the releative order
  of operation as seen from another thread, the main thread might see
  a new updated value of ~total_time~ while seeing outdated value of
  ~num_done~ giving an overestimation of average.

Possible solution to the above problem: Using Mutex with non atomic
variables.

** Example: ID Allocation

Usecase: Give a new unique number everytime a function is called.

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicU32;
  use std::sync::atomic::Ordering::Relaxed;

  fn allocate_new_id() -> u32 {
      static NEXT_ID: AtomicU32 = AtomicU32::new(0);
      NEXT_ID.fetch_add(1, Relaxed)
  }

  fn main() {
      for _ in 0..=4 {
	  let id = allocate_new_id();
	  println!("id: {id}");
      }
  }
#+end_src

#+RESULTS:
: id: 0
: id: 1
: id: 2
: id: 3
: id: 4

Problem with the above code: It overflows on reaching it's maximum
number.

One solution: Stop incrementing beyond a certian number

#+begin_src rust :results value verbatim :exports both
  use std::sync::atomic::AtomicU32;
  use std::sync::atomic::Ordering::Relaxed;

  fn allocate_new_id() -> u32 {
      static NEXT_ID: AtomicU32 = AtomicU32::new(0);
      let id = NEXT_ID.fetch_add(1, Relaxed);
      assert!(id < 1000, "too many IDs!");
      id
  }

  fn main() {
      let id = allocate_new_id();
      println!("id: {id}");
  }
#+end_src

#+RESULTS:
: id: 0

Cons: What if after the ~fetch_add~ statement, there are multiple
threads calling the function making the number overlfow. The assert
won't be even triggered in some cases!

Three common solutions:
- std::process::abort instead of assertion. While aborting the process
  might take a brief moment in which the function can still be called
  by other threads, the chance of that happening billions of times
  before the program is truly aborted is negligible.
- Second solution:

#+begin_example rust
fn allocate_new_id() -> u32 {
    static NEXT_ID: AtomicU32 = AtomicU32::new(0);
    let id = NEXT_ID.fetch_add(1, Relaxed);
    if id >= 1000 {
        NEXT_ID.fetch_sub(1, Relaxed);
        panic!("too many IDs!");
    }
    id
}
#+end_example

But even here it is possible to be briefly increment beyond 1000
between fetch_add and fetch_sub call.

- Third solution: You need to learn about compare and exhange
  operations.

* Compare and Exchange Operations

- This operation checks if the atomic value is equal to a given value,
  and only if that is the case does it replace it with a new value,
  all atomically as a single operation.
- It will return the previous value and tell us whether it replaced it
  or not.

#+begin_example rust
impl AtomicI32 {
    pub fn compare_exchange(
        &self,
        expected: i32,
        new: i32,
        success_order: Ordering,
        failure_order: Ordering
    ) -> Result<i32, i32>;
}
#+end_example

It's good to think it like this:

#+begin_example rust
impl AtomicI32 {
    pub fn compare_exchange(&self, expected: i32, new: i32) -> Result<i32, i32> {
        // In reality, the load, comparison and store,
        // all happen as a single atomic operation.
        let v = self.load();
        if v == expected {
            // Value is as expected.
            // Replace it and report success.
            self.store(new);
            Ok(v)
        } else {
            // The value was not as expected.
            // Leave it untouched and report failure.
            Err(v)
        }
    }
}
#+end_example

compare and exchange is the most general operation. You can implement
other atomic operations via this. Example:

#+begin_example rust
fn increment(a: &AtomicU32) {
    let mut current = a.load(Relaxed);
    loop {
        let new = current + 1;
        match a.compare_exchange(current, new, Relaxed, Relaxed) {
            Ok(_) => return,
            Err(v) => current = v,
        }
    }
}
#+end_example

There is also *compare_exchange_weak* method. The difference is that
the weak version may still sometimes leave the value untouched and
return an Err, even though the atomic value matched the expected
value. No idea why someone would want that, but the book promises that
we will learn about it in chapter 7.

** Example: Lazy One Time Initialization

Use case: Avoid the previous con that we saw.

#+begin_src rust :crates '((rand . 0.8.5)) :results value verbatim :exports both
  use rand::Rng;
  use std::sync::atomic::AtomicU64;
  use std::sync::atomic::Ordering::Relaxed;

  fn calculate_x() -> u64 {
      let mut rng = rand::thread_rng();
      let random: u64 = rng.gen_range(1..100);
      println!("Generated random");
      random
  }

  fn get_x() -> u64 {
      static X: AtomicU64 = AtomicU64::new(0);
      let mut x = X.load(Relaxed);
      if x == 0 {
	  x = calculate_x();
	  X.store(x, Relaxed);
      }
      x
  }

  fn main() {
      std::thread::scope(|s| {
	  s.spawn(|| {
	      let x = get_x();
	      println!("Thread 1: {x}");
	  });
	  s.spawn(|| {
	      let x = get_x();
	      println!("Thread 2: {x}");
	  });
      });
      println!("Done");
  }
#+end_src

#+RESULTS:
: Generated random
: Thread 1: 57
: Generated random

That's not what we want because we are getting different values. Let's
fix it:

#+begin_src rust :crates '((rand . 0.8.5)) :results value verbatim :exports both
  use rand::Rng;
  use std::sync::atomic::AtomicU64;
  use std::sync::atomic::Ordering::Relaxed;

  fn calculate_x() -> u64 {
      let mut rng = rand::thread_rng();
      let random: u64 = rng.gen_range(1..100);
      println!("Generated random");
      random
  }

  fn get_x() -> u64 {
      static X: AtomicU64 = AtomicU64::new(0);
      let mut x = X.load(Relaxed);
      if x == 0 {
	  let new_x = calculate_x();
	  match X.compare_exchange(0, new_x, Relaxed, Relaxed) {
	      Ok(_) => new_x,
	      Err(v) => v,
	  }
      } else {
	  x
      }
  }

  fn main() {
      std::thread::scope(|s| {
	  s.spawn(|| {
	      let x = get_x();
	      println!("Thread 1: {x}");
	  });
	  s.spawn(|| {
	      let x = get_x();
	      println!("Thread 2: {x}");
	  });
      });
      println!("Done");
  }
#+end_src

: Generated random
: Generated random
: Thread 2: 87
: Thread 1: 87
: Done
