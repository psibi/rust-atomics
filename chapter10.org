* Chapter 10: Ideas and Inspiration

* Semaphore

- A semaphore is effectively just a counter with two operations:
  - *signal*: Also called up or V
  - *wait*: Also called down or P
- Signal operation increments the counter up to certain maximum.
- Wait operation decrements the counter. If it is zero, a wait
  operation will block and wait for a matching signal operation
  preventing the counter to become negative.
- Implementation ideas:
  - Semaphore can be implemented as a combination of Mutex<u32> for
    the counter and Condvar for wait operation to wait for.
  - Can be also implemented as a single AtomicU32 on platforms that
    support futex like operations.
- *Binary semaphore*: Semaphore with a maximum value of one is called
  binary semaphore.
- [[https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html][Semaphore in tokio]]
  - wait: wait is called as [[https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html#method.acquire][acquire]]
  - signal: No signal operation! Drop on permit will increase the counter up.

Example code:

#+begin_src rust :crates '((tokio . *)) :features '((tokio . ("sync" "macros" "rt-multi-thread")))
  use tokio::sync::Semaphore;

  #[tokio::main]
  async fn main() {
      let semaphore = Semaphore::new(3);

      {
	  let a_permit = semaphore.acquire().await.unwrap();
	  assert_eq!(semaphore.available_permits(), 2);
      }

      assert_eq!(semaphore.available_permits(), 3);
      println!("Program finished");
  }
#+end_src

* RCU

- Movtivation: Multiple threads to mostly read and (sometimes) mutate
  data, you can use *RwLock*.
- RCU: Read, copy and update.

* Lock free linked list

- The idea is that you have atomic pointer to the struct to point to
  the next one to turn it into a linked list.

* Queue Based Locks

- For most standard locking primitives, the operating system’s kernel
  keeps track of the threads that are blocked on it, and is
  responsible for picking one to wake up when asked to do so. An
  interesting alternative is to implement a mutex (or other locking
  primitive), by manually keeping track of the queue of waiting
  threads.
- [[https://github.com/kprotty/usync][Rust crate: usync]]

* Parking Lot based locks

- Idea: Move the queue into a global data structure. This way mutex
  only needs to be a single byte.
- The global data structure can be a HashMap that maps memory
  addresses to a queue of threads waiting on the mutex at that
  address. This global data structure is often called a parking lot,
  since it’s a collection of parked threads.

* Sequence Lock

- A sequence lock is another solution to the problem of atomically
  updating (larger) data without using traditional (blocking)
  locks. It uses an atomic counter that is odd while the data is being
  updated, and even when the data is ready to be read.
- The writing thread will have to increment the counter from even to
  odd before mutating the data, after which it has to increment the
  counter again to leave it at a (different) even value.
- Any reading thread can, at any point and without blocking, read the
  data by reading the counter both before and after. If the two values
  from the counter are equal and even, there was no concurrent
  mutation, meaning you read a valid copy of the data. Otherwise, you
  might have read data that was concurrently being modified, in which
  case you should just try again.
