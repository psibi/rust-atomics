* Chapter 7: Understanding the Processor

- Goal of the chapter is to understand how atomics work at the
  processor level.
- Focuses on two processor architectures:
  - x86-64: The 64 bit version of x86 architecture. Also called as
    AMD64.
  - ARM64: The 64-bit version of the ARM architecture used by nearly
    all modern mobile devices, high performance embedded systems. Also
    known as AArch64.

* Processor Instructions

Example snippet of assembly for some made up architecture:

#+begin_example asm
ldr x, 1234 // load from memory address 1234 into x
li y, 0     // set y to zero
inc x       // increment x
add y, x    // add x to y
mul x, 3    // multiply x by 3
cmp y, 10   // compare y to 10
jne -5      // jump five instructions back if not equal
str 1234, x // store x to memory address 1234
#+end_example

- In this example, x and y are names of registers. Registers are part
  of the processor, not of the main memory, and usually hold a single
  integer or memory address.
- On 64-bit architectures, they are generally 64 bits in size.

Various tools to see machine code:
- objdump
- [[https://crates.io/crates/cargo-show-asm][cargo-show-asm]]
- [[https://godbolt.org/][Compiler explorer by Matt Godbolt]]

** Rust code

#+begin_example rust
pub fn add_ten(num: &mut i32) {
    *num += 10;
}
#+end_example

*** Equivalent ARM64 assembly

#+begin_example asm
add_ten:
    ldr w8, [x0]
    add w8, w8, #10
    str w8, [x0]
    ret
#+end_example

- Both ~w8~ and ~x0~ are registers.
- ~x0~ register contains the argument to the function ~num~ which is
  the address of the ~i32~.
- ~ldr~ instruction loads the 32-bit value from that memory address
  into the ~w8~ register.
- ~add~ instruction adds ten to w8 and stores the result into w8
  register back.
- ~ret~ instruction marks the end of the function and causes the
  processor to jump back and continue with the function that called
  ~add_ten~.
- Example of reducied instruction set computer (RISC).

*** Equivalent x86-64 assembly

#+begin_example asm
add_ten:
    add dword ptr [rdi], 10
    ret
#+end_example

- The ~dword ptr~ prefix in the assembly specifies that it a 32-bit
  operation.
- Register called ~rdi~ is used for the ~num~ argument.
- On x86_64, a single ~add~ instruction does what it takes three
  instructions for ARM64: load, incrementing and storing.
- Example of complex instruction set computer (CISC).

* Load and Store

** Rust code

#+begin_example rust
pub fn a(x: &mut i32) {
    *x = 0;
}
#+end_example

*** Equivalent x86-64 assembly

#+begin_example asm
a:
    mov dword ptr [rdi], 0
    ret
#+end_example

- Instruction ~mov~ is used to copy ("move") data from one place to
  another.

*** Equivalent ARM64 assembly

#+begin_example asm
a:
    str wzr, [x0]
    ret
#+end_example

- The ~str~ instruction stands for store register. It is used to store
  32 bit register into memory.
- ~wzr~ is a special register which always contains zero.

Now let's try atomic store:

** Rust code

#+begin_example rust
pub fn a(x: &AtomicI32) {
    x.store(0, Relaxed);
}
#+end_example

*** Equivalent x86-64 assembly

#+begin_example asm
a:
    mov dword ptr [rdi], 0
    ret
#+end_example

*** Equivalent ARM64 assembly

#+begin_src rust
a:
    str wzr, [x0]
    re
#+end_src

Observations:

- The assembly is identical to the non atomic version.
- mov and str instructions are already atomic.
- Any difference between &mut i32 and &AtomicI32 here is only relevant
  for the compiler checks and optimizations, but is meaningless for
  the processors.

Same things happens for relaxed atomic load operations:

** Rust code

#+begin_example rust
pub fn a(x: &i32) -> i32 {
    *x
}
#+end_example

and

#+begin_example rust
pub fn a(x: &AtomicI32) -> i32 {
    x.load(Relaxed)
}
#+end_example

*** Equivalent x86-64 assembly (for both cases)

#+begin_example asm
a:
    mov eax, dword ptr [rdi]
    ret
#+end_example

- Here the ~mov~ instruction is used to copy from memory into the
  32-bit eax regiser.

*** Equivalent ARM64 assembly (for both cases)

#+begin_example asm
a:
    ldr w0, [x0]
    ret
#+end_example

- The ~ldr~ instruction is used to load the memory from ~x0~ register
  into ~w0~ register.

General observation:

- The 32-bit eax and w0 registers are used for passing back a 32-bit
  return value of a function. (For 64-bit values, the 64-bit rax and
  x0 registers are used.)

* Read-Modify-Write Operations

- Things get far more interesting for read-modify-write operations
  such as addition.
- A non-atomic read-modify-write operation usually compiles to three
  separate instructions (read, modify, and write) on a RISC
  architecture like ARM64, but can often be done in a single
  instruction on a CISC architecture like x86-64.

** Rust code

#+begin_example rust
pub fn a(x: &mut i32) {
    *x += 10;
}
#+end_example

*** Equivalent ARM64 assembly

#+begin_example asm
a:
    ldr w8, [x0]
    add w8, w8, #10
    str w8, [x0]
    ret
#+end_example

- Not atomic as loading and storing happens in separate steps.

*** Equivalent x86-64 assembly

#+begin_example asm
a:
    add dword ptr [rdi], 10
    ret
#+end_example

- While not directly obvious from the assembly itself, the x86-64
  version is not atomic.
- The add instruction will be split by the processor into several
  microinstructions behind the scenes, with separate steps for loading
  the value and storing the result.
- This would be irrelevant on a single-core computer, as switching a
  processor core between threads generally only happens between
  instructions. However, when multiple cores are executing
  instructions in parallel, we can no longer assume instructions all
  happen atomically without considering the multiple steps involved in
  executing a single instruction.

** x86 lock prefix

- To support multi-core systems, Intel introduced an instruction
  prefix called lock. It is used as a modifier to instructions like
  add to make their operation atomic.
- The lock prefix can only be applied to a very limited number of
  instructions, including ~add~, ~sub~, ~and~, ~not~, ~or~, and ~xor~,
  which are all very useful operations to be able to do atomically.
- The ~xchg~ (exchange) instruction, which corresponds to the atomic
  swap operation, has an implicit lock prefix: it behaves like lock
  xchg regardless of the lock prefix.

Let's compare atomic add now:

#+begin_example rust
pub fn a(x: &AtomicI32) {
    x.fetch_add(10, Relaxed);
}
#+end_example

Equivalent x86-64 assembly code:

#+begin_example asm
a:
    lock add dword ptr [rdi], 10
    ret
#+end_example

- The difference between atomic and non atomic version is the lock
  prefix.

What if we change our rust code to this:

#+begin_example rust
pub fn a(x: &AtomicI32) -> i32 {
    x.fetch_add(10, Relaxed)
}
#+end_example

- Here, ~fetch_add~ returns the previous value.

Equivalent x86-64 assembly code:

#+begin_example asm
a:
    mov eax, 10
    lock xadd dword ptr [rdi], eax
    ret
#+end_example

- ~xadd~ instruction does exchange and add. Basically it puts the
  originally loaded value into a register.
- Other than ~xadd~ and ~xchg~, none of the other lock prefixable
  instructions, like ~sub~ and ~or~ have such a variant. For
  subtraction that's no issue, as ~xadd~ can be used with a negative
  value.
- For ~and~, ~or~ and ~xor~ operations that affect only a single bit
  such as ~fetch_or(1)~ or ~fetch_and(!1)~, it's possible to use the
  ~bts~ (bit test and set), ~btr~ (bit test and reset), and ~btc~ (bit
  test and complement) instructions. These instructions allow a ~lock~
  prefix, change only a single bit and make the previous value of that
  one bit available for an instruction that follows such as a
  conditional jump.
- When these operations affect more than one bit, they cannot be
  represented by a single x86-64 instruction.
- Similary ~fetch_min~ and ~fetch_max~ operations have no
  corresponding x86-64 instruction. For these operations, we need a
  different strategy than a simple ~lock~ prefix.

** x864 compare and exchange instructions

- We saw in chapter 2, how atomic fetch and modify operation can be
  implemented as a compare and exchange loop.
- This is what the compiler will do for operations that cannot be
  represented by a single x86-64 instruction since the architecture
  does include a (lock-prefixable) cmpxchg (compare and exchange)
  instruction.

Let's try a new Rust code:

#+begin_example rust
pub fn a(x: &AtomicI32) -> i32 {
    x.fetch_or(10, Relaxed)
}
#+end_example

- [[https://doc.rust-lang.org/std/sync/atomic/struct.AtomicI32.html#method.fetch_or][fetch_or docs]]

Equivalent x86-64 assembly code:

#+begin_example asm
a:
    mov eax, dword ptr [rdi]
.L1:
    mov ecx, eax
    or ecx, 10
    lock cmpxchg dword ptr [rdi], ecx
    jne .L1
    ret
#+end_example

- First mov instruction loads the atomic variable (the argument in the
  function ~a~) into the eax register.
- The following mov copies the value into ~ecx~ register.
- The following or instruction performs the binary or operation and
  store the result in ~ecx~ register. So this is what the register will have:
  - eax: The original value passed to the function.
  - ecx: The result of the or operation.
- The cmpxchg is same as the Rust equivalent one. See the
  [[https://doc.rust-lang.org/std/sync/atomic/struct.AtomicI32.html#method.compare_exchange][Rust
  docs]] if you don't remember.

This is the syntax for cmpxchg instruction:

- Format: cmpxchg [memory_location], new_value
- ~cmpxchg~ instruction will compare it's first operand with eax
  register. If they are same, it will replace the second operand is
  loaded into the first operand. Otherwise, the first operand is
  loaded into eax register.
- [[https://www.felixcloutier.com/x86/cmpxchg][More details on cmpxchg instruction]]

Let's return back to the assembly code:
- So the ~cmpxchg~ instruction will check with the eax register and
  the rdi register. Since they will be same, it will replace the first
  operand with the value in the ecx register.
- Return value is already stored in the eax register.

On x86-64, there is no difference between compare_exchange and
compare_exchange_weak. Both compile down to a ~lock cmpxchng~
instruction.

** Load-Linked and Store-Conditional Instructions

- The closest thing to a compare-and-exchange loop on a RISC
  architecture is a load-linked/store-conditional (LL/SC) loop.
- It involves two special instructions that come in a pair: a
  load-linked instruction, which mostly behaves like a regular load
  instruction, and a store-conditional instruction, which mostly
  behaves like a regular store instruction.
- They are used in a pair, with both instructions targeting the same
  memory address.
- The key difference to the regular load and store instructions is
  that the store is conditional: it refuses to store to memory if any
  other thread has overwritten that memory since the load-linked
  instruction.
- These two instructions allow us to load a value from memory, modify
  it, and store the new value back only if nobody has overwritten the
  value since we loaded it. If that fails, we can simply retry. Once
  it succeeds, we can safely pretend the whole operation was atomic,
  since it didn’t get disrupted.

The key to making these instructions feasible and efficient to
implement is twofold:
- only one memory address (per core) can be tracked at a time.
- the store-conditional is allowed to have false negatives, meaning
  that it may fail to store even though nothing has changed that
  particular piece of memory.

This makes it possible to be less precise when tracking changes to
memory, at the cost of perhaps a few extra cycles through an LL/SC
loop. Access to memory could be tracked not per byte, but per chunk of
64 bytes, or per kilobyte, or even the entire memory as a whole. Less
accurate memory tracking results in more unnecessary cycles through
LL/SC loops, significantly reducing performance, but also reducing
implementation complexity.

** ARM load-exclusive and store-exclusive

- ldxr (load exclusive register)
- stxr (store exclusive register)
- clrex (clear exclusive): This instruction can be used as an
  alternative to strx to stop tracking writes to memory without
  storing anything.

Let's see how atomic addition code translates to ARM64:

#+begin_src rust
pub fn a(x: &AtomicI32) {
    x.fetch_add(10, Relaxed);
}
#+end_src

Compile ARM64:

#+begin_src asm
a:
.L1:
    ldxr w8, [x0]
    add w9, w8, #10
    stxr w10, w9, [x0]
    cbnz w10, .L1
    ret
#+end_src

- We load the atomic variable into ~w8~ register.
- ~add~ instruction adds the value in w8 and 10 and puts into w9
  register.
- ~stxr~ stores zero in ~w10~ if succeeded or a one if it didn't.
  - It checks if the memory location pointed by ~[x0]~ is modified. If
    it didn't modify, it replaces its content with the value in ~w9~
    register and stores 1 in ~w10~ register.
  - If the value pointed by ~[x0]~ was modified, it stores 0 in ~w10~
    register.
- The ~cbnz~ is a compare and branch on non zero instruction. If it is
  zero, it will jump to L1.

Other observations:
- This LL/SC pattern is quite flexible: it doesn’t just work for a
  limited set of operations like add and or, but for virtually any
  operation.
- We can just as easily implement an atomic fetch_divide or
  fetch_shift_left by putting the corresponding instruction(s) between
  the ldxr and stxr instructions.
- However, if there are too many instructions between them, there’s an
  increasingly high chance of disruption resulting in extra
  cycles. Generally, the compiler will attempt to keep the number of
  instructions in an LL/SC pattern as small as possible, to avoid
  LL/SC loops that would rarely—or even never—succeed and thus could
  spin forever.

Note that later version of ARM64 includes new CISC style instructions
for atomic apperations:
- ladd: Load and add instruction equivalent to atomic fetch_add
  without the need for an LL/SC loop.
- cas: Compare and swap instruction corresponding to
  compare_exchange. When this instruction is used, there is no
  difference between compare_exchange and compare_exchange_weak just
  like on x86-64.
