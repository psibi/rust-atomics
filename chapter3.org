* Chapter 3: Memory Ordering

* Reordering and Optimizations

- Compiler and Processors might decide to reorder or rewrite parts of
  your program if it has reason to believe it might result in faster
  execution.
- It only does that if that wouldn’t change the behavior of your
  program.

Example code:

#+begin_example rustic
fn f(a: &mut i32, b: &mut i32) {
    *a += 1;
    *b += 1;
    *a += 1;
}
#+end_example

Compiler will understand that the orders doesn't matter since nothing
happens between these three addition operations that depends on the
value of *a or *b (Assuming overflow checking is disabled since
without it there can be a crash on any of the statements).

So compiler can optimize it like this:

#+begin_example rustic
fn f(a: &mut i32, b: &mut i32) {
    ,*a += 2;
    ,*b += 1;
}
#+end_example

While executing the function a processor might for a variety of
reasons end up executing the second addition before the first
addition, possibly because *b was available in a cache, while *a had
to be fetched from the main memory.

The logic for verifying that a specific reordering or other
optimization won’t affect the behavior of your program *does not* take
other threads into account.

In our example above, that’s perfectly fine. The only situation where
this is a problem is when mutating data that’s shared between
threads. Or, in other words, when working with atomics.

This is why we have to explicitly tell the compiler and processor what
they can and can’t do with our atomic operations, since their usual
logic ignores interactions between threads and might allow for
optimizations that do change the result of your program. You tell them
via *std::sync::atomic::Ordering*

The available orderings in Rust are:
- Relaxed ordering: Ordering::Relaxed
- Release and acquire ordering: Ordering::{Release, Acquire, AcqRel}
- Sequentially consistent ordering: Ordering::SeqCst

In C++, there is also something called consume ordering.

* The Memory Model

- Rust’s memory model is mostly copied from C++.
- They describe the different memory ordering options and their formal
  definition and for compiler writers to know exactly what guarantees
  they need to provide to us.

** Happens-Before Relationship

- The memory model defines the order in which operations happen in
  terms of happens-before relationships.

Rules:

- Same thread: Happens in order. If a thread is executing f(); g();,
  then f() happens-before g().
- Between threads: Happens-Before relationship only occur in a few
  specific cases:
  - Spawning and Joining a thread
  - Unlocking and locking a mutex
  - Atomic operations that use non relaxed memory ordering

*Relaxed* memory ordering is the most basic (and most performant)
 memory ordering that, by itself, never results in any cross thread
 happens-before relationships.

Let's look at the example code where function ~a~ and ~b~ are
concurrently executed by different threads:

#+begin_example rustic
static X: AtomicI32 = AtomicI32::new(0);
static Y: AtomicI32 = AtomicI32::new(0);

fn a() {
    X.store(10, Relaxed);     # Step 1
    Y.store(20, Relaxed);     # Step 2
}

fn b() {
    let y = Y.load(Relaxed);  # Step 3
    let x = X.load(Relaxed);  # Step 4
    println!("{x} {y}");
}
#+end_example

Since we know Relaxed memory ordering never results in any cross
thread happens before relationships, these are the possible outputs:
- 0 0
- 10 20
- 10 0
- And a more counter-intuitive output of 20 0

Let's look into how ~20 0~ is a valid output:
- There is *no* possible globally consistent order of the four
  operations that would result in this outcome.
- When Step 3 is executed, there is no happens-before relationship
  with Step 2, which means it could load either 0 or 20.
- When Step 4 is executed, there is no happens-before relationship
  with Step 1, which means it could load either 0 or 10. Given this,
  the output 0 20 is a valid outcome.
- The important and counter-intuitive thing to understand is that
  operation Step 3 loading the value 20 does not result in a
  happens-before relationship with Step 2, even though that value is
  the one stored by Step 2.
- A more practical and intuitive, but less formal, understanding is
  that from the perspective of the thread executing b, operations Step
  1 and Step 2 might appear to happen in the opposite order.

** Spawning and Joining

- Spawning a thread creates a happens-before relationship between what
  happened before the spawn() call, and the new thread.
- Similarly, joining a thread creates a happens-before relationship
  between the joined thread and what happens after the join() call.

To demonstrate, the assertion in the following example cannot fail:

#+begin_src rustic :results value verbatim :exports both
  use std::sync::atomic::AtomicI32;
  use std::sync::atomic::Ordering::Relaxed;
  use std::thread;

  static X: AtomicI32 = AtomicI32::new(0);

  fn main() {
      X.store(1, Relaxed);
      let t = thread::spawn(f);
      X.store(2, Relaxed);
      t.join().unwrap();
      X.store(3, Relaxed);
  }

  fn f() {
      let x = X.load(Relaxed);
      assert!(x == 1 || x == 2);
      println!("x: {x}");
  }
#+end_src

#+RESULTS:
: x: 2

Guarantees in the above code:
- Load of X happens after the first store of 1 because of
  happens-before relationship formed by the spawn operation.
- Whether the load of X observes 1 or 2 is unpredictable: It could be
  1 or 2, but not 0 or 3 because join operation also forms the happens
  before relationship.

Let's see if we can force the output to be 1:

#+begin_src rustic :results value verbatim :exports both
  use std::sync::atomic::AtomicI32;
  use std::sync::atomic::Ordering::Relaxed;
  use std::thread;

  static X: AtomicI32 = AtomicI32::new(0);

  fn main() {
      X.store(1, Relaxed);
      let t = thread::spawn(f);
      thread::sleep(std::time::Duration::from_millis(500));
      X.store(2, Relaxed);
      t.join().unwrap();
      X.store(3, Relaxed);
  }

  fn f() {
      let x = X.load(Relaxed);
      assert!(x == 1 || x == 2);
      println!("x: {x}");
  }
#+end_src

#+RESULTS:
: x: 1


* Relaxed Ordering

- *Relaxed* memory ordering is the most basic (and most performant)
  memory ordering that, by itself, never results in any cross thread
  happens-before relationships.
- They do guarantee a total modification order of each individual
  atomic variable. This means that all modifications of the same
  atomic variable happen in an order that is the same from the
  perspective of every single thread.

Example code to demonstrate the concept where a and b are concurrently
executed by different threads:

#+begin_example rustic
static X: AtomicI32 = AtomicI32::new(0);

fn a() {
    X.fetch_add(5, Relaxed);
    X.fetch_add(10, Relaxed);
}

fn b() {
    let a = X.load(Relaxed);
    let b = X.load(Relaxed);
    let c = X.load(Relaxed);
    let d = X.load(Relaxed);
    println!("{a} {b} {c} {d}");
}
#+end_example

Possible output:

- 0 0 0 0
- 5 5 5 5
- 0 5 5 15

But total modification order guarantees that this is impossible:

- 0 5 0 15
- 0 0 10 15

The idea is that all threads will agree on a single order.

* Release and Acquire Ordering

- Release and acquire memory ordering are used in a pair to form a
  happens-before relationship between threads.
- Release memory ordering applies to store operations, while Acquire
  memory ordering applies to load operations.
- A happens-before relationship is formed when an acquire-load
  operation observes the result of a release-store operation.
- AcqRel is used to represent the combination of Acquire and Release,
  which causes both the load to use acquire ordering, and the store to
  use release ordering.

| Ordering | Operation |
|----------+-----------|
| Release  | Store     |
| Acquire  | Load      |

Let's see an example program: Send 64 bit integer from a spawned
thread to the main thread.

#+begin_src rustic :results value verbatim :exports both
  use std::sync::atomic::Ordering::{Acquire, Relaxed, Release};
  use std::sync::atomic::{AtomicBool, AtomicU64};
  use std::thread;
  use std::time::Duration;

  static DATA: AtomicU64 = AtomicU64::new(0);
  static READY: AtomicBool = AtomicBool::new(false);

  fn main() {
      thread::spawn(|| {
	  DATA.store(123, Relaxed);
	  READY.store(true, Release); // Everything from before this store ..
      });
      while !READY.load(Acquire) {
	  // .. is visible after this loads `true`.
	  thread::sleep(Duration::from_millis(100));
	  println!("waiting...");
      }
      println!("{}", DATA.load(Relaxed));
  }
#+end_src

#+RESULTS:
: waiting...
: 123

In the above code, these are the important observations:
- Spawned thread uses a Release store to set READY flag.
- When main thread observes this through its acquire load operation, a
  happens-before relationship is established between these two
  operations.
- If we used Relaxed ordering for all the operations, the main thread
  could still load zero from the ~DATA~ atomic variable.

Introduction:
- Mutexes are common use case for release and acquire ordering.
- Demonstration of the pattern:

#+begin_example rustic
static mut DATA: String = String::new();
static LOCKED: AtomicBool = AtomicBool::new(false);

fn f() {
    if LOCKED.compare_exchange(false, true, Acquire, Relaxed).is_ok() {
        // Safety: We hold the exclusive lock, so nothing else is accessing DATA.
        unsafe { DATA.push('!') };
        LOCKED.store(false, Release);
    }
}

fn main() {
    thread::scope(|s| {
        for _ in 0..100 {
            s.spawn(f);
        }
    });
}
#+end_example

** Example: Lazy Initialization with Indirection

- Use case: In our previous example on chapter 2, we did lazy
  initialization of Atomic values. But what if we want to do
  initialization of complex values which does not fit into atomic
  variable ?

#+begin_src rustic :crates '((rand . 0.8.5)) :results value verbatim :exports both
  use rand::Rng;
  use std::sync::atomic::AtomicPtr;
  use std::sync::atomic::Ordering::{Acquire, Release};

  #[derive(Debug)]
  struct MyData {
      rand1: u64,
      rand2: u64,
  }

  fn calculate_x() -> MyData {
      let mut rng = rand::thread_rng();
      let rand1: u64 = rng.gen_range(1..100);
      let rand2: u64 = rng.gen_range(1..100);
      println!("Generated random");
      MyData { rand1, rand2 }
  }

  fn get_x() -> &'static MyData {
      static PTR: AtomicPtr<MyData> = AtomicPtr::new(std::ptr::null_mut());

      let mut p = PTR.load(Acquire);

      if p.is_null() {
          p = Box::into_raw(Box::new(calculate_x()));
          if let Err(e) = PTR.compare_exchange(std::ptr::null_mut(), p, Release, Acquire) {
              // Safety: p comes from Box::into_raw right above,
              // and wasn't shared with any other thread.
              drop(unsafe { Box::from_raw(p) });
              p = e;
          }
      }

      // Safety: p is not null and points to a properly initialized value.
      unsafe { &*p }
  }

  fn main() {
      std::thread::scope(|s| {
          s.spawn(|| {
              let x = get_x();
              println!("Thread 1: {x:?}");
          });
          s.spawn(|| {
              let x = get_x();
              println!("Thread 2: {x:?}");
          });
      });
      println!("Done");
  }
#+end_src

#+RESULTS:
: Generated random
: Thread 1: MyData { rand1: 94, rand2: 48 }
: Generated random
: Thread 2: MyData { rand1: 94, rand2: 48 }
: Done

* Sequentially Consistent Ordering

- The strongest memory ordering is sequentially consistent ordering:
  Ordering::SeqCst.
- It includes all the guarantees of acquire ordering (for loads) and
  release ordering (for stores), and also guarantees a globally
  consistent order of operations.
- While it might seem like the easiest memory ordering to reason
  about, SeqCst ordering is almost never necessary in practice. In
  nearly all cases, regular acquire and release ordering suffice.

Example that depends on sequentially consistent ordered operations:

#+begin_src rustic :results value verbatim :exports both
  use std::sync::atomic::AtomicBool;
  use std::sync::atomic::Ordering::SeqCst;
  use std::thread;

  static A: AtomicBool = AtomicBool::new(false);
  static B: AtomicBool = AtomicBool::new(false);

  static mut S: String = String::new();

  fn main() {
      let a = thread::spawn(|| {
          A.store(true, SeqCst);
          if !B.load(SeqCst) {
              unsafe { S.push('!') };
          }
      });

      let b = thread::spawn(|| {
          B.store(true, SeqCst);
          if !A.load(SeqCst) {
              unsafe { S.push('!') };
          }
      });

      a.join().unwrap();
      b.join().unwrap();
  }
#+end_src

Observations:
- Possiblity of ~S~ variable to be empty since both thread do the
  store operation.
- It's impossible for both thread to write to ~S~. Only one thread can
  at a maximum write to ~S~.

All real world uses of SeqCst involves a similar pattern of store that
must be globally visible before a subsequent load on the same
thread. For these situations, a potentially more efficient alternative
is to instead use relaxed operations in combination with a SeqCst
fence

* Fences

- An atomic fence allows you to separate the memory ordering from the
  atomic operation.
- This can be useful if you want to apply a memory ordering to
  multiple operations, or if you only want to apply it conditionally.
- Release-store can be split into a release fence followed by a
  relaxed store:

| Operation            | Equivalent           |
|----------------------+----------------------|
| a.store(1, Release); | fence(Release);      |
|                      | a.store(1, Relaxed); |

Similary:

| Operation        | Equivalent       |
|------------------+------------------|
| a.load(Acquire); | a.load(Relaxed); |
|                  | fence(Acquire);  |

- Using a separate fence can result in an extra processor instruction,
  which can be less efficient.
- std::sync::atomic::fence function represents an atomic fence
  - Release: Release fence
  - Acquire: Acquire fence
  - AcqRel or SeqCst (SeqCst fence additionally also takes part in the
    sequentially consistent total order)
- A fence is not tied to any single atomic variable. This means that a
  single fence can be used for multiple variables at once.

- [[https://en.cppreference.com/w/cpp/atomic/atomic_thread_fence][Good CPP reference on guarantee by fences]]
