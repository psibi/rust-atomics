* Chapter 5: Building your own Channels

- Channels can be used to send data between threads.
- Various variants:
  - One sender, One receiver
  - Multiple senders, One receiver
  - Multiple receivers
  - Some channels are blocking, meaning the receiving (and sometimes
    sending) is a blocking operation.
  - Some optimized for throughput while others are optimized for low
    latency.

* A Simple Mutex-Based Channel

#+begin_src rustic :results value verbatim :exports both
  use std::collections::VecDeque;
  use std::sync::{Condvar, Mutex};

  pub struct Channel<T> {
      queue: Mutex<VecDeque<T>>,
      item_ready: Condvar,
  }

  impl<T> Channel<T> {
      pub fn new() -> Self {
	  Self {
	      queue: Mutex::new(VecDeque::new()),
	      item_ready: Condvar::new(),
	  }
      }

      pub fn send(&self, message: T) {
	  self.queue.lock().unwrap().push_back(message);
	  self.item_ready.notify_one();
      }

      pub fn receive(&self) -> T {
	  let mut b = self.queue.lock().unwrap();
	  loop {
	      if let Some(message) = b.pop_front() {
		  return message;
	      }
	      b = self.item_ready.wait(b).unwrap();
	  }
      }
  }

  fn main() {
      std::thread::scope(|s| {
	  let channel = Channel::new();
	  channel.send("Hello world");
	  s.spawn(move || {
	      let msg = channel.receive();
	      println!("Received msg: {msg}");
	  });
      });
  }
#+end_src

#+RESULTS:
: Received msg: Hello world

Cons of the above channel:
- Not bounded
- Every single send/receive will briefly block since they all use the
  same Mutex.

* An Unsafe One-Shot Channel

Usecase: Sending exactly one message from one thread to another.

Possible approach:
- Use above implementation, but change ~VecDeque~ to ~Option~. But it
  will still suffer from the same con as listed above (only the second
  one).
- Use the SpinLock approach we saw in last chapter. Instead of option,
  we use ~MaybeUnint<T>~ for saving space in memory.

#+begin_src rustic :results value verbatim :exports both
  use std::cell::UnsafeCell;
  use std::mem::MaybeUninit;
  use std::sync::atomic::{AtomicBool, Ordering};

  pub struct Channel<T> {
      message: UnsafeCell<MaybeUninit<T>>,
      ready: AtomicBool,
  }

  unsafe impl<T> Sync for Channel<T> where T: Send {}

  impl<T> Channel<T> {
      pub const fn new() -> Self {
	  Self {
	      message: UnsafeCell::new(MaybeUninit::uninit()),
	      ready: AtomicBool::new(false),
	  }
      }

      pub fn is_ready(&self) -> bool {
	  self.ready.load(Ordering::Acquire)
      }

      /// Safety: Only call this once!
      pub unsafe fn send(&self, message: T) {
	  (*self.message.get()).write(message);
	  self.ready.store(true, Ordering::Release);
      }

      /// Safety: Only call this once,
      /// and only after is_ready() returns true!
      pub unsafe fn receive(&self) -> T {
	  (*self.message.get()).assume_init_read()
      }
  }

  fn main() {
      let channel = Channel::new();
      std::thread::scope(|s| {
	  unsafe {
	      &channel.send("Hello world");
	  };
	  s.spawn(move || {
	      let msg = unsafe { &channel.receive() };
	      println!("Received msg: {msg}");
	  });
      });
  }
#+end_src

#+RESULTS:
: Received msg: Hello world

Observations:
- We tell compiler that the Channel is safe to be shared between
  threads as long as the underlying data T is ~Send~.
- We make the methods unsafe to put the correct API usage on the users
  hand.
- No Drop trait implemented. The MaybeUninit type does not track
  whether it has been initialized or not, and will therefore not
  automatically drop its contents when dropped. This means that if a
  message is sent but never received, the message will never be
  dropped.
